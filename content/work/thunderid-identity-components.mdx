## Problem

Every app that adds sign-in eventually needs the screens *after* sign-in: view and edit your profile, change your password, manage your account. Developers usually build these from scratch, once per framework, and they drift out of sync with the identity backend.

ThunderID ships SDKs for React, Next.js, Vue, Nuxt and Express. The goal of the self-service work is that a developer can drop in a component, get a working profile flow, and make it look like *their* product rather than ours.

## Constraints

- **Five frameworks, one behaviour.** A component has to feel native in React and in Vue, render correctly under Next.js and Nuxt server rendering, and have an Express story for server-rendered apps, without five diverging implementations.
- **Themeable without forking.** Integrators need to change colour, radius, typography and density. If the only way is to override internal class names, every SDK release breaks someone's styles.
- **Composable.** Some teams want the full drop-in component, others want the parts (a field, a section, a hook) to build their own layout.
- **Accessible by default.** These components become someone else's product, so keyboard and screen-reader support can't be optional.
- **Lives in a monorepo.** Changes go through review with other SDK maintainers, so small, well-scoped PRs matter.

## Approach

<ThunderArchitectureDiagram />

The architecture separates **what the component does** from **how a framework renders it**:

1. **Shared logic in the core.** Data fetching, validation and state transitions for a self-service flow live in framework-agnostic code. Every SDK runs the same rules.
2. **Thin framework bindings.** Each SDK exposes the flow in that framework's idiom: components and hooks in React, components and composables in Vue, server-aware wrappers for Next.js and Nuxt.
3. **A theme contract, not a stylesheet.** Components read design tokens exposed as CSS custom properties. An integrator sets tokens once on the provider and every component follows.
4. **Composition over configuration.** The drop-in component is built out of the same smaller parts that are exported for custom layouts.

### Why tokens instead of a `className` escape hatch

Class-name overrides couple the integrator to the component's DOM. Rename a wrapper and their styles silently break. Tokens are a public API: `--radius` means the same thing in every component and every framework, and they can be versioned like any other API.

The playground below runs on the same idea. The theme editor writes tokens, and the component only reads them. The site you're reading uses the same token system, so you can apply your theme to the whole page.

```tsx
// The integrator's whole theming surface: tokens on the provider.
<IdentityProvider
  theme={{
    colors: { primary: "#C6F432" },
    radius: 6,
    typography: { fontFamily: "Inter" },
    density: "comfortable",
  }}
>
  <UserProfile />
</IdentityProvider>
```

### Keeping five SDKs honest

The risk with five SDKs is behaviour drift: a field validates in React but not in Vue. Keeping validation and state in shared code means a fix lands once.
